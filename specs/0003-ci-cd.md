# CI, CD and releases

The workflows in `.github/workflows/` check, build, test and publish through the scripts in `scripts/`. `checks.yml` runs the checks that need no Chromium; `ci.yml` runs on pull requests to main and `cd.yml` on pushes to main; both share the build steps in `.github/actions/build`.

## Machines

Every target compiles on the organization's runner service, `lanescape/runners`, through `lanescape/actions`, on `lanescape-80vcpu-linux-amd64-spot`: macOS is cross-compiled there too. Each target is tested on a machine like it: `linux-amd64` on `lanescape-16vcpu-linux-amd64`, `linux-arm64` on `lanescape-16vcpu-linux-arm64`, and `macos-arm64` on Blacksmith's `blacksmith-12vcpu-macos-26`. The checks and CD's version and publish jobs run on `lanescape-2vcpu-linux-amd64`. Nothing else uses Blacksmith or GitHub's hosted runners, except a fork's pull request: the service makes no machines for forks, and a fork can't build Chromium on GitHub's runners, so a fork's run does only the checks, on `ubuntu-26.04`, and the jobs that build or test require the pull request's head repository to be this one.

A job names its selector alone in `runs-on`, as the service requires, and sets its machine up in its own steps.

## Work disks

A build is the expensive part, so each target has a work-disk family, named for the target in `.github/runners.json`, mounted at `/work`, which holds depot_tools, the checkout, its build directory and the Debian sources' download cache. A family's key covers what decides its build: the pin, `.gclient`, settings, the GN target, the patches and `targets.json` (`scripts/check.py` keeps that list complete). The service restores a run's own disk for the key, else its newest whatever the key, else main's for the key, else main's newest, else none; the build steps check what they find and rebuild only what's out of date.

- **main** restores and saves main's disks: every successful CD build saves its target's disk, so main's are always those of its newest build.
- **A pull request** restores its own, else main's, so its first build compiles only what it changed relative to main's newest build, and later pushes only what changed since. It saves its own, which go when it closes, and never main's.

A cold build, with no disk, can outlast one machine: the service stops a job at 90 minutes, or a Spot machine is preempted, and reruns the job up to 3 attempts in all from the disk it left, where the steps carry on. Every build job's name is unique for that reason. Removing a family from `.github/runners.json` on main deletes its disks.

## CI

On a pull request, `ci.yml` runs the checks, builds all three targets and tests each on its machine. A new push cancels the run in progress. A failed compile, package or test fails its job; a skipped job is only ever a fork's.

- **Checks** (`checks.yml`), needing no Chromium: the scripts' tests (`tests/scripts`), the repository's checks (`scripts/check.py`: every script compiles, the pin is well formed, the disk families match the targets and their keys, every action is pinned to a commit, README lists every spec), and `actionlint` over the workflows.
- **Build**, for each target: check out, patch, configure and build Chromium, package the SDK, extract the package's `lib`, `headers`, `toolchain` and `sysroot` parts into an empty directory, and build the test embedder there with `tests/embedder/build.py`, outside Chromium's tree, with nothing but the SDK's toolchain and `sdk.json`. The embedder, with the runtime files beside it, goes to its test machine as an artifact kept for 3 days. A pull request's version is `<Chromium tag>-pr<number>`, which is never published.
- **Test**, for each target: run the embedder (`tests/embedder/test.sh`), which installs the system libraries Chromium loads on a Linux machine, starts Content with its sandbox, loads a page whose script computes a value, reads the value back through JavaScript in an isolated world, and exits 0 only if it is right, within 3 minutes.

The macOS build signs in to Google Cloud with GitHub's OIDC token to read the Apple SDK (specs/0002-build.md, macOS), so its job alone has `id-token: write`, through the workload identity provider and service account the repository variables `APPLE_SDK_WORKLOAD_IDENTITY_PROVIDER` and `APPLE_SDK_SERVICE_ACCOUNT` name, which must grant nothing beyond reading that object. Every other job has `contents: read` at most.

## CD

On a push to main, `cd.yml`:

1. **Version**: decides the version before anything builds, so the packages and manifest carry it (Versions, below), and writes it, or why there is none, to the job summary.
2. **Build** and **Test**, as in CI, with the version, and the build also writes the corresponding source (specs/0004-licences.md) and keeps every asset as an artifact for 7 days.
3. **Publish**: checks the version is still the next, gathers every job's assets, writes the manifest and publishes the release (Publishing, below).

CD's runs go one at a time, each in its turn, in the order they began to wait, and none is cancelled, waiting or running (GitHub's `concurrency` with `queue: max`), so every commit on main gets a release of its own, up to GitHub's 100 waiting, past which it cancels the newest; then the maintainer reruns that run once the queue has room. If a commit still ends up without a release of its own, its changes ship in the next commit's, and that run's job summary lists every commit since the previous release that wasn't released on its own. A run that publishes nothing, because its commit isn't newer than every released commit, succeeds and says why.

## Versions

A version is `<Chromium tag>-<revision>` (specs/0001-sdk.md, Versions), and its release's tag is `v<version>`. Nothing in the repository records a revision; `scripts/version.py main` derives it from the tags:

- The revision is the highest revision of any `v<Chromium tag>-<n>` tag for the commit's pin, plus one, or 1 if there is none. Every commit on main gets one, including one that changes nothing the binaries are made from: its binaries match the previous version's, and that is intended.
- A commit publishes only if it is a strict descendant of every release tag's commit, newer than everything released. A rerun of an older run therefore publishes nothing, and never ships older content as a newer revision. A revert that restores older inputs is a new commit, so it gets a new revision: versions only move forward.

## Publishing

`scripts/publish.py` is the one interface to the releases: `gather` merges the jobs' assets, refusing two jobs' different copies of one asset; `manifest` writes `manifest.json`, which lists every asset with its size and SHA-256, and `SHA256SUMS`, and fails, naming the asset, if any asset is 2 GiB or larger; `release` publishes. Releases are on GitHub, as GitHub releases of this repository, holding each version's binaries, notices and corresponding source together.

`release` refuses if the version's tag exists or a published release for it does, deletes a draft for the version that a failed run left, creates a new draft, uploads every asset, checks each uploaded asset's size and SHA-256 against the manifest, and only then publishes the draft, which creates the tag at the commit last, and checks the tag names the commit. A failure before that leaves a draft, which is never visible as a release. It never changes or deletes a published release or a tag. Only the publish job has `contents: write`, with the workflow's own `GITHUB_TOKEN`; nothing logs the token, or any URL an upload or download is given.

Every version stays published. GitHub keeps releases and their assets until someone deletes them, so retention is the maintainer's to set: the design assumes at least 3 years, as the licences' source offers need, and no automation deletes a release. GitHub's immutable releases setting, where available, stops anyone changing a published release or its tag, and is a backstop the maintainer can turn on.
