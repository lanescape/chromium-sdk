# CI, CD and releases

The workflows in `.github/workflows/` check, build, test and publish through the scripts in `scripts/`. `checks.yml` runs the checks that need no Chromium; `target.yml` is one target's chain, its build, embedder and test jobs; `ci.yml` runs on pull requests to main and `cd.yml` on pushes to main, and each calls `checks.yml` once and `target.yml` once for each target. The chain's jobs share their steps through `.github/actions/build` and `.github/actions/embedder`.

## Machines

Every target compiles on the organization's runner service, `lanescape/runners`, through its actions, `lanescape/runners/actions/<name>@v1`, on `lanescape-80vcpu-linux-amd64-spot`: macOS is cross-compiled there too. The builds alone use that machine. Every target's test embedder is built on `lanescape-16vcpu-linux-amd64`. Each target is tested on a machine like it, as `targets.json`'s `test_runner` names it: `linux-amd64` on `lanescape-16vcpu-linux-amd64`, `linux-arm64` on `lanescape-16vcpu-linux-arm64`, and `macos-arm64` on Blacksmith's `blacksmith-6vcpu-macos-26` (`scripts/check.py` keeps `target.yml` the same). The checks and CD's version and publish jobs run on `lanescape-2vcpu-linux-amd64`. Nothing else uses Blacksmith or GitHub's hosted runners, except a fork's pull request: the service makes no machines for forks, and a fork can't build Chromium on GitHub's runners, so a fork's run does only the checks, on `ubuntu-26.04`, and `ci.yml` calls each target's chain only if the pull request's head repository is this one.

A job names its selector alone in `runs-on`, as the service requires, and sets its machine up in its own steps.

## Caches

Compiling Chromium is the expensive part. A build job asks for its work disk, which the runner service gives it empty, mounted at `/work`: 150 GB, room for the checkout and a build directory, which together have come to at most 58 GB, with 10,000 IOPS and 2,400 MiB/s, since moving their many small files in and out of caches is bound by the disk's operations, and takes three times as long at the service's default, 3,000 IOPS. A Hyperdisk Balanced disk's size, IOPS and throughput are each paid for, and at 150 GB it allows up to 75,000 IOPS, 500 for each GB, and with 10,000 IOPS provisioned, up to 2,400 MiB/s, a quarter of its IOPS, so the smaller disk keeps the same performance; and keeps what's slow to make again as caches, which `.github/runners.json` declares and `target.yml`'s build alone restores and saves, with the service's actions `cache` and `save-cache`. Nothing else uses a work disk or a cache: the checks, the test embedder's build, the tests and publishing set their machines up in their own steps and download what they need, such as the packaged SDK, as workflow artifacts from the build job, and save nothing; the corresponding source's Debian downloads go to the job's temporary directory. There are two kinds of cache, and only the build's output is saved every time:

- **`chromium-checkout`**, shared by every target, holds `/work` but for the build directories: depot_tools (`/work/depot_tools`) and the checkout (`/work/chromium`), synced and patched, with the records `scripts/sdk.py` keeps there. Its key is exactly `chromium/pin.json`, `chromium/gclient` and the patches, which decide its files: the checkout is saved patched, and patching again after a patch changes touches files, so a changed patch makes a new key. `linux-amd64`'s build saves it, after its build, only when the restored checkout wasn't the one for its key (`save-cache` with `if: inputs.target == 'linux-amd64' && !endsWith(steps.restored.outputs.checkout, '_exact')`), so once for each key, leaving out `lost+found`, the build directories and the build's marker (below). The macOS build adds the Apple SDK to its checkout, so it never saves it, and no cache ever holds the Apple SDK; `linux-arm64` has no need to.
- **`chromium-out-<target>`**, one for each target in `targets.json`, holds that target's build directory, `/work/chromium/src/out/<target>`, restored into the checkout. Its key is everything that decides what the target's build compiles: the pin, `.gclient`, settings, every file of the GN target, the patches, `targets.json` and `scripts/sdk.py`, which writes the build's arguments, so the same key means the same inputs. Every build saves it, after its build.

`scripts/check.py` keeps both keys complete, and the steps that save them as above. The service saves a cache only from a job that succeeds, and chooses the version a run restores once for each cache, the first time one of the run's jobs asks, so every target's build in a run restores the same checkout: for its key, else its newest whatever the key, first in the run's own scope and then in main's. All builds run on `amd64` machines, macOS's too, so every target shares that architecture's caches. The build steps check what they find and rebuild only what's out of date: a checkout of another pin is synced to the pin, which leaves unchanged files their times, and another patch is reverted and the new one applied, which leaves files that come out the same their times; the caches keep every file's time to the nanosecond, so with the checkout restored, then its build directory, the build is incremental.

The two caches are chosen apart, so a build directory can have been built from another state of the checkout than the one restored, as when a pull request's own newest build directory meets main's newer checkout, and the files that differ can be older than what was built from them. So `configure` records in the build directory what it is built from, and after restoring both the build runs `scripts/sdk.py reconcile`, which makes the files of each patch that differs, and the GN target's copy, newer than anything built, so they rebuild, and removes the build directory, so that it's built afresh, if it was built from another pin or `.gclient`, from a checkout that isn't whole, or for macOS against another Apple SDK than the pinned one (specs/0002-build.md).

- **main** restores main's caches, and saves main's: every successful CD build saves its target's build directory, so main's are always those of its newest build, and `linux-amd64`'s saves the checkout for a key main hasn't saved.
- **A pull request** restores its own, else main's, so its first build compiles only what it changed relative to main's newest build, and later pushes only what changed since. It saves its own, which go when it closes, and never main's.

The first run after the caches replace work disks finds none, and builds cold. A cold build, with no caches, can outlast one machine: the service stops a job at 90 minutes, or a Spot machine is preempted, and reruns the job, up to 3 attempts of the run in all, on a work disk made from the job's resume image, where the steps carry on. Every build job's name is unique for that reason: `Build <target>`, in a call named for its target, so GitHub shows it as `<target> / Build <target>`. A build writes `/work/.libchromium-restored`, with where its checkout came from, once it has restored and reconciled its caches; a rerun that finds it restores nothing, so it carries on from its resume image rather than going back to the caches, which would undo the lost job's work, and saves the checkout only if the lost job would have. A rerun that doesn't find it restores and reconciles again.

## CI

On a pull request, `ci.yml` runs the checks, then builds all three targets and tests each on its machine. A new push cancels the run in progress (`concurrency` with `cancel-in-progress`). A failed compile, package or test fails its job; a skipped job is only ever a fork's, or one after a failure.

Each target is a chain of its own, `target.yml`, called with the target: **Build** → **Embedder** → **Test**, each needing the one before, and every chain needing the checks. A failure stops its own chain and no other: no job starts once a job before it in its chain has failed, and no chain starts if the checks fail. The other targets' chains carry on, so one push still shows every target that builds and passes.

- **Checks** (`checks.yml`), needing no Chromium: the scripts' tests (`tests/scripts`), the repository's checks (`scripts/check.py`: every script compiles, the pin is well formed, `.github/runners.json` declares the checkout's cache and one build directory's for each target, with their keys, only `target.yml`'s build has a work disk and caches, it saves its build directory every time, and only `linux-amd64` saves the checkout, the runner service's actions are named by their tag, `lanescape/runners/actions/<name>@v1`, never by `lanescape/actions`, where they were, and every other action is pinned to a commit, the build asks for its work disk as below, the Apple SDK the workflows fetch is the one `targets.json` pins, the workflows' shape and permissions (below), every artifact is kept 1 day, README lists every spec), and `actionlint` over the workflows, configured by `.github/actionlint.yaml` with the runner labels it can't know.
- **Build**, for each target, on its work disk: restore the caches, check out, patch, configure and build Chromium, and package the SDK, which goes to the next job as the artifact `sdk-<target>`. A pull request's package is a quick one, at zstd level 3 and without `symbols`; CD's is whole, at level 19, and only a whole one is ever published (specs/0002-build.md, Quick packages). Artifacts belong to the run, and calls of `target.yml` share their caller's, so each target's names are its own in the run, and CD's publish job finds every target's. A pull request's version is `<Chromium tag>-pr<number>`, which is never published.
- **Embedder**, for each target, on a fresh `lanescape-16vcpu-linux-amd64` with no Chromium checkout: extract the package's `lib`, `headers`, `toolchain` and `sysroot` parts into an empty directory and build the test embedder there with `tests/embedder/build.py`, with nothing but the SDK's toolchain and `sdk.json` (and for macOS, the Apple SDK, which this job fetches as an embedder would bring its own). The embedder, with the runtime files beside it, goes to its own target's test machine as the artifact `embedder-<target>`.
- **Test**, for each target: run the embedder (`tests/embedder/test.sh`), which installs the system libraries Chromium loads on a Linux machine, starts Content with its sandbox, loads a page whose script computes a value, reads the value back through JavaScript in an isolated world, and exits 0 only if it is right, within 3 minutes.

**Artifacts are intermediate**, and every one, in CI and CD, is kept for 1 day (`retention-days: 1`, which `scripts/check.py` requires of every upload), as a resume image can resume a job for a day. A rerun more than a day later, of a failed test or of CD's publish job alike, finds its run's artifacts gone, and the whole run must be rerun, which rebuilds. CD's publish job refuses unless every target's `sdk-<target>` is there, so a rerun of it alone never publishes fewer targets than `targets.json` names. Releases are not artifacts, and never expire (Publishing, below).

The macOS build and the macOS embedder job alone sign in anywhere but GitHub, to fetch the Apple SDK (Credentials, below). Every other job but CD's publish job (Publishing, below) has `contents: read` at most.

A called workflow's jobs get their token from the job that calls it, and can narrow but never widen it. So `ci.yml` and `cd.yml` grant each call `contents: read`, and the `macos-arm64` call alone also `id-token: write`. In `target.yml`, the build and the embedder set no permissions of their own, and get their call's grant; the test sets `contents: read`, so not even macOS's has `id-token`. A job of `target.yml` can't ask for `id-token: write` itself: GitHub refuses a called job that asks for more than its call grants, and the Linux calls grant no `id-token`. As a backstop, a Linux target's build and embedder fail at their first step if they could ask for an OIDC token. `scripts/check.py` keeps this shape: each workflow calls `target.yml` once for each target in `targets.json`, and every call grants exactly the above and needs the checks, and in CD the version job, and nothing else, so no chain waits on another; CI has no jobs but the checks and the calls, which skip forks; CD's calls run only if the version job says the commit publishes, and CD's publish job needs every call; the chain is build → embedder → test, and neither its jobs nor the publish job set a condition of their own, so each runs only if every job it needs succeeded; nothing runs past a failure (`continue-on-error`, `always()`, `cancelled()` or `failure()`); only the build runs on `lanescape-80vcpu-linux-amd64-spot`, and the test on its target's `test_runner`; `checks.yml`, `ci.yml` and `cd.yml` grant nothing by default, and every job has exactly `contents: read` but the calls of `target.yml`, CD's publish job (`contents: write`), and `target.yml`'s build and embedder, which set no permissions and take their call's grant, as `target.yml` sets none for the whole workflow; and `.github/actions/apple-sdk` is used only by `target.yml`'s build and embedder, in a step whose own condition limits it to `macos-arm64`. It reads the workflows and actions line by line, so it refuses YAML it couldn't read as GitHub does: anything but plain keys directly followed by their colon, each level indented 2 spaces more than its parent, with plain or one-line quoted values, `{}`, flat flow sequences or block scalars, and no anchors, aliases, tags, merge keys or flow mappings.

### Timing the macOS link

For now, while the maintainer finds out why it runs on one core for most of its twelve minutes where Linux's takes about a minute, the macOS link of `libchromium.dylib` writes a time trace: `//libchromium:chromium`'s Mac `ldflags` add `-Wl,--time-trace=libchromium-link-trace.json`, in the build directory, leaving out events shorter than 50 ms. lld's trace names each phase it times, on the thread that ran it, with the module or file it worked on, and its ThinLTO backends' work too. After the build, the macOS build job's step **Summarize the macOS link's time trace** prints, with `scripts/link_trace.py`, what ran in the link's last stretch, the threads that finished last, with the wall time their events cover, waits included, the longest events and each phase's sum, to the job's log and summary, then deletes the trace, so the build directory's cache doesn't keep it unless deleting it fails. The step never fails the build, though the link itself fails if lld can't write the trace, and a build that doesn't link the library has no trace, and says so. Neither changes what's built or shipped: `sdk.json` takes its link flags from `:embedder_probe`'s link, not the library's. Both go once the link is understood.

## Credentials

The macOS build and the macOS embedder job each copy the pinned Apple SDK (specs/0002-build.md, macOS) onto their machine with `.github/actions/apple-sdk`, which hard-codes the archive's object, `gs://lanescape-ci-tools/macos/sdk/26.2/MacOSX26.2.sdk.tar.zst`, and its SHA-256 (`scripts/check.py` keeps both the same as `targets.json`'s), and checks the copy's SHA-256 before anything uses it. It is a step of their own in `target.yml`, which runs only for `macos-arm64` and hands the archive to `.github/actions/build` or `.github/actions/embedder`. They sign in to Google Cloud with GitHub's OIDC token, through workload identity federation, so those two jobs alone have `id-token: write`, from the `macos-arm64` call's grant (CI, above). The provider and the account are fixed in the action, and aren't secrets: the provider `projects/168731703350/locations/global/workloadIdentityPools/lanescape-ci-tools/providers/github`, which must accept only tokens from the `lanescape` organization's repositories, and the service account `lanescape-ci-tools-reader@lanescape-dev.iam.gserviceaccount.com`, which must be able only to read the objects of `gs://lanescape-ci-tools`, the organization's one private bucket of platform tools for every repository's CI. The organization's infrastructure makes the bucket, the pool and the account, not this repository.

The runner service plays no part in this: its machines are plain Debian 13, and the job fetches the SDK itself. A fork's pull request never runs these jobs (Machines, above), so it never signs in. Nothing logs the credentials, and the archive stays in the job's temporary directory: it is never in an artifact, a package or a release.

## CD

On a push to main, `cd.yml`:

1. **Version**: decides the version before anything builds, so the packages and manifest carry it (Versions, below), and writes it, or why there is none, to the job summary.
2. **Checks**, as in CI, alongside the version.
3. Each target's chain, **Build** → **Embedder** → **Test**, as in CI, once the checks pass and only if the version step says the commit publishes, with the version; the build also writes the corresponding source (specs/0004-licences.md) into its artifact.
4. **Publish**, needing the version, the checks and every target's chain: checks the version is still the next and that every target's artifact is there (CI, above: artifacts are kept a day), gathers every target's assets, checks every part of every target is there and none is a quick package, writes the manifest and publishes the release (Publishing, below). If any target's chain fails or is skipped, nothing is published.

CD's runs go one at a time, each in its turn, in the order they began to wait, and none is cancelled, waiting or running (GitHub's `concurrency` with `queue: max`), so every commit on main gets a release of its own, up to GitHub's 100 waiting, past which it cancels the newest; then the maintainer reruns that run once the queue has room. If a commit still ends up without a release of its own, its changes ship in the next commit's, and that run's job summary lists every commit since the previous release that wasn't released on its own. A run that publishes nothing, because its commit isn't newer than every released commit, succeeds and says why.

## Versions

A version is `<Chromium tag>-<revision>` (specs/0001-sdk.md, Versions), and its release's tag is `v<version>`. Nothing in the repository records a revision; `scripts/version.py main` derives it from the tags:

- The revision is the highest revision of any `v<Chromium tag>-<n>` tag for the commit's pin, plus one, or 1 if there is none. Every commit on main gets one, including one that changes nothing the binaries are made from: its binaries match the previous version's, and that is intended.
- A commit publishes only if it is a strict descendant of every release tag's commit, newer than everything released. A rerun of an older run therefore publishes nothing, and never ships older content as a newer revision. A revert that restores older inputs is a new commit, so it gets a new revision: versions only move forward.

## Publishing

`scripts/publish.py` is the one interface to the releases: `gather` merges the jobs' assets, refusing two jobs' different copies of one asset; `manifest` writes `manifest.json`, which lists every asset with its size and SHA-256 and, under `source`, where the source is that the release points to rather than copies (specs/0004-licences.md, Corresponding source), and `SHA256SUMS`, and fails, naming the asset, if any asset is 2 GiB or larger; `release` publishes. Releases are on GitHub, as GitHub releases of this repository, holding each version's binaries, notices and corresponding source together. A release's notes say where its source is: the `source-*` assets, and, as in the manifest, Chromium's source tarball and its checksums, the Chromium tag and commit, and this repository's patch at the release's tag and commit.

`release` refuses if Chromium's source tarball for the pin or its checksums file isn't published, which it asks for without credentials, so that a release never points to source that isn't there; then it refuses if the version's tag exists or a published release for it does, deletes a draft for the version that a failed run left, creates a new draft, uploads every asset, checks each uploaded asset's size and SHA-256 against the manifest, and only then publishes the draft, which creates the tag at the commit last, and checks the tag names the commit. A failure before that leaves a draft, which is never visible as a release. It never changes or deletes a published release or a tag. Only the publish job has `contents: write`, with the workflow's own `GITHUB_TOKEN`; nothing logs the token, or any URL an upload or download is given.

Every version stays published. GitHub keeps releases and their assets until someone deletes them, so retention is the maintainer's to set: the design assumes at least 3 years, as the licences' source offers need, and no automation deletes a release. GitHub's immutable releases setting, where available, stops anyone changing a published release or its tag, and is a backstop the maintainer can turn on.
